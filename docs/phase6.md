# フェーズ 6: 本番向け仕上げの実装計画

## 概要

本番公開に向けて、サイト全体の SEO、OGP、RSS、サイトマップ、404 ページ、デプロイ設定を整えます。
<br>あわせて、現在の検証用コンテンツだけの状態から、公開時に読める技術記事と読了本を追加し、一覧、検索、タグ、アーカイブが実データで機能することを確認します。

Phase 4 と Phase 5 で設定したページ固有のメタ情報を土台に、サイト名、公開 URL、canonical URL、SNS 共有画像などの共通ルールを一元管理します。

既存の別リポジトリから Cloudflare に公開しているブログを、本リポジトリの Nuxt ブログへ置き換えます。既存の本番ドメインを引き継ぎ、旧サイトの URL と新サイトの URL を比較して、必要なページには 301 リダイレクトを設定します。

Cloudflare Pages / Workers のどちらを利用しているかと現在のビルド設定を最初に確認し、その構成に合わせて静的生成または SSR の方式を決定します。

## 想定ファイル構成

```txt
app/
  error.vue

public/
  images/
    og/
      yuris-blog-ogp.png

server/
  routes/
    rss.xml.ts

content/
  articles/
    2026/
      *.md
  books/
    2026/
      *.md

nuxt.config.ts
.env.example
```

導入するモジュールや設定によって、次のファイルも追加候補とします。

```txt
public/
  robots.txt
  _redirects

wrangler.jsonc
```

`_redirects` は Cloudflare Pages でリダイレクトが必要な場合、`wrangler.jsonc` は Workers または Wrangler によるデプロイで必要な場合だけ追加します。

## サイト共通設定

サイト名、サイト説明、公開 URL、作者名など、複数ページで使う値を一元管理します。

想定する環境変数:

```dotenv
# 既存ブログの本番ドメインへ置き換える
NUXT_PUBLIC_SITE_URL=https://blog.example.com
```

設定方針:

- 公開 URL は末尾の `/` を除いた絶対 URL として扱う
- ローカル開発では `http://localhost:3010` をフォールバックとして利用できるようにする
- 本番ビルドでは公開 URL が未設定のままにならないよう確認する
- canonical、OGP、RSS、サイトマップで同じ公開 URL を参照する
- サイト名、説明、作者名は `app.config.ts` または `runtimeConfig.public` にまとめる
- `NUXT_PUBLIC_SITE_URL` には既存ブログの本番ドメインを設定する
- Cloudflare のプレビュー環境では、プレビュー URL を canonical に使用しない
- SNS アカウントなど未確定の値はコードへ仮置きしない

## SEO メタ情報

### サイト全体

- `htmlAttrs.lang` を `ja` にする
- サイト名を含む共通の title template を設定する
- サイト説明、作者名、theme color、favicon を設定する
- `og:type`、`og:site_name`、`og:locale` を共通設定する
- X 向けに `twitter:card` を設定する
- canonical URL は公開 URL と現在の path から絶対 URL で生成する
- 一覧の `?page=2` など、内容が変わるクエリは canonical に必要な範囲だけ残す
- 検索結果や存在しないページをインデックス対象にしない

### ページ別

- トップページはサイト名とサイト全体の説明を使う
- 記事詳細は記事タイトル、`description`、公開日、更新日、タグ、サムネイルを使う
- 読了本詳細は書名、著者、読書メモであることが分かる説明、表紙を使う
- 記事詳細の `og:type` は `article` とし、公開日と更新日を設定する
- 一覧、タグ、年別アーカイブ、プロフィールは各ページ固有の title と description を維持する
- ページネーションの 2 ページ目以降は title と canonical にページ番号を反映する
- サムネイルや表紙がない場合はサイト共通 OGP 画像へフォールバックする

構造化データは初回公開の必須範囲を絞り、トップページの `WebSite` と技術記事の `BlogPosting` を候補とします。値の重複や不正な URL がないことを確認してから導入します。

## OGP 画像方針

初回公開では、動的な OGP 画像生成を導入せず、次の優先順位で既存画像を利用します。

1. 技術記事の `thumbnail`
2. 読了本の `cover`
3. サイト共通の `/images/og/yuris-blog-ogp.png`

画像方針:

- サイト共通 OGP 画像は `1200 x 630 px` で用意する
- OGP メタには公開 URL を付けた絶対 URL を設定する
- 画像形式は PNG、JPEG、WebP のうち、SNS クローラーで安定して扱える形式を使う
- 画像にはサイト名と内容が判別できる十分なコントラストを持たせる
- 記事サムネイルと書籍表紙を OGP に使う場合は、共有カードで極端にトリミングされないか確認する
- `og:image:width`、`og:image:height`、`og:image:alt` を可能な範囲で設定する
- 外部サイトの書影 URL へ直接依存せず、利用許諾を確認した画像を `public/` 配下で管理する

記事タイトルを合成した動的 OGP は、記事数が増えて手作業が負担になった段階で別フェーズとして検討します。

## RSS

公開済みの技術記事を対象に `/rss.xml` を提供します。

出力項目:

- サイトタイトル
- サイト説明
- サイト URL
- フィード URL
- 記事タイトル
- 記事 URL
- 記事説明
- 公開日時
- 更新日時
- タグ

実装方針:

- `queryCollection('articles')` から `published: true` の記事だけを取得する
- `publishDate` の降順で並べる
- 各記事 URL とフィード URL は絶対 URL にする
- XML 内の特殊文字を正しくエスケープする
- `Content-Type` を RSS/XML として返す
- サイトの `<head>` に RSS の discovery link を追加する
- 静的生成後も `/rss.xml` が成果物に含まれるよう prerender 対象にする
- 初回は記事の description を配信し、Markdown 本文全文は配信しない

RSS 用ライブラリを追加する場合は、XML のエスケープや仕様準拠を安全に扱えることを理由とし、既存依存だけで簡潔に実装できるか比較してから決めます。

## サイトマップと robots

サイトマップには、検索エンジンへ公開するページだけを含めます。

対象:

- `/`
- `/profile`
- `/articles`
- `/books`
- 公開済みの記事詳細
- 公開済みの読了本詳細
- 実在するタグ別ページ
- 実在する年別アーカイブ

除外:

- `published: false` のコンテンツ
- 存在しないタグ、年、ページ番号
- 開発用 URL
- 404 ページ

実装方針:

- `@nuxtjs/sitemap` と `@nuxtjs/robots` を利用する
- Nuxt Content の公開済みデータから動的 URL を追加する
- Nuxt Content の自動収集は使わず、`published: true` の記事と読了本だけを専用 API から渡す
- 実在する公開コンテンツからタグ別ページと年別アーカイブの URL を生成する
- canonical と同じ公開 URL を使う
- `robots.txt` からサイトマップの URL を案内する
- 本番ではクロールを許可し、プレビュー環境では `noindex` またはクロール拒否を選べるようにする
- 生成された XML に重複 URL や localhost が含まれていないことを確認する

モジュールに Nuxt の固定ルート検出、絶対 URL 化、XML 生成、`robots.txt` との連携を任せ、公開状態の判定だけをアプリ側で管理します。

## 404 ページ

Nuxt の `app/error.vue` を使い、存在しないページをサイト共通の見た目で表示します。

表示内容:

- 404 であることが分かる見出し
- ページが見つからなかったことを伝える短い説明
- トップページへ戻るボタン
- 記事一覧へ移動するボタン
- 必要に応じてサイト内検索を開く導線

表示方針:

- 404 以外のエラーでは、ステータスに応じた汎用メッセージを表示する
- エラーページ単体でヘッダー相当のサイトロゴとテーマが破綻しないようにする
- Nuxt UI の semantic color を使い、ライト / ダークモードに対応する
- モバイルでもボタンと本文が画面内に収まるようにする
- エラーページには `noindex` を設定する
- 戻るボタンだけに依存せず、確実に存在するページへのリンクを用意する

## 公開用コンテンツの追加

現在の技術記事と読了本は表示確認用の内容なので、本番公開前に実際に読めるコンテンツを追加します。

初回公開の目安:

- 技術記事: 既存分を含めて 3〜5 件
- 読了本: 既存分を含めて 3〜5 件

追加方針:

- 技術記事は `content/articles/{年}/{slug}.md` に追加する
- 読了本は `content/books/{年}/{slug}.md` に追加する
- slug は半角英数字とハイフンを基本とし、公開後は不用意に変更しない
- frontmatter は `content.config.ts` の schema に従う
- 公開前の下書きは `published: false` にする
- `publishDate` と `updated` は `YYYY-MM-DD` で統一する
- タグの大文字・小文字や表記を既存コンテンツと統一する
- 記事の `description` は一覧、検索結果、SEO、RSS で単独でも意味が通る文章にする
- サムネイルと表紙はそれぞれ `public/images/articles/`、`public/images/books/` で管理する
- 画像の権利、代替テキスト、ファイルサイズを確認する

公開前チェック:

- タイトル、説明、日付、著者、出版社、タグに誤りがない
- 見出し階層が `h2` から自然に続いている
- リンク切れや仮テキストがない
- コード例に秘密情報や個人情報が含まれていない
- 一覧、詳細、検索、タグ、アーカイブ、関連記事に正しく反映される
- 1 件しかない状態では確認できなかったページネーションや関連コンテンツの挙動を実データで確認する

実際の記事本文、読了本、書影はユーザーの原稿と利用可能な素材を使います。内容が未確定の場合、無断で架空の公開記事や書籍情報を作らず、下書きテンプレートの追加までに留めます。

## デプロイ設定

既存の Cloudflare プロジェクトが参照する Git リポジトリを、本リポジトリへ切り替えてブログを置き換えます。切り替え前に現在の設定を記録し、プレビュー環境で新ブログを検証してから本番ブランチを変更します。

最初に確認する項目:

- 既存環境が Cloudflare Pages / Workers のどちらか
- 現在接続されている Git リポジトリと本番ブランチ
- ビルドコマンド、出力ディレクトリ、Node.js と pnpm のバージョン
- 本番ドメイン、DNS、環境変数、互換性フラグ
- 旧サイトの全 URL と検索流入があるページ

移行方針:

- 完全静的構成の場合は `pnpm generate` と `.output/public` を基本候補にする
- Workers / SSR 構成の場合は Cloudflare 向け Nitro preset と互換性設定を確認する
- `NUXT_PUBLIC_SITE_URL` を本番環境へ設定する
- Node.js と pnpm のバージョンをデプロイ環境で固定する
- RSS、サイトマップ、404、動的 route の prerender 結果を確認する
- プレビュー環境が検索インデックスへ登録されないようにする
- 環境変数や秘密情報をリポジトリへコミットしない
- 旧 URL を維持できないページは新 URL への 301 リダイレクトを設定する
- 削除するページは、代替ページがある場合だけリダイレクトし、無関係なトップページへ一律転送しない
- 独自ドメインと DNS は可能な限り既存設定を維持する
- 切り替え直前の旧サイトと Cloudflare 設定を記録し、問題発生時の復旧手順を用意する
- 切り替え後に HTTPS、末尾スラッシュ、リダイレクトループを確認する
- 静的アセットと HTML のキャッシュヘッダーを確認する
- Cloudflare 上での 404 のステータスと配信方法を確認する
- デプロイプレビューに `noindex` を設定する

## 旧サイトからの URL 移行

既存ブログの評価と外部リンクを失わないよう、切り替え前に旧 URL の一覧を作成します。

- 旧サイトのサイトマップ、記事一覧、公開済みページから URL を収集する
- 新サイトで同じ内容を公開するページは、可能なら旧 URL を維持する
- URL が変わるページは旧 URL と新 URL の対応表を作る
- Cloudflare Pages では必要に応じて `public/_redirects` に 301 リダイレクトを定義する
- Workers を使う場合は既存ルーティングとの競合を確認してリダイレクトを実装する
- リダイレクト元と転送先の canonical が矛盾しないことを確認する
- 旧 RSS、サイトマップ、画像 URL を参照している利用者への影響を確認する
- 移行後は主要な旧 URL が 301 を返し、新 URL が 200 を返すことを確認する

## 実装ステップ

1. サイト共通設定を整理する
   - サイト名、説明、作者名、公開 URL の管理場所を決める
   - `.env.example` に公開 URL を追加する
   - canonical と絶対 URL を生成する共通処理を作る

2. SEO メタ情報を統一する
   - 共通 title template と基本メタを設定する
   - 各ページの title、description、canonical、OGP を確認する
   - 記事詳細へ記事用メタ情報を追加する
   - 必要な構造化データを追加する

3. OGP 画像を整える
   - サイト共通 OGP 画像を追加する
   - 記事サムネイル、書籍表紙、共通画像のフォールバックを実装する
   - すべての OGP 画像 URL を絶対 URL にする

4. RSS を追加する
   - `/rss.xml` を実装する
   - 公開済み記事を日付の降順で出力する
   - RSS discovery link と prerender 設定を追加する

5. サイトマップと robots を追加する
   - 必要なモジュールまたは生成処理を選定する
   - 固定ページと公開済みコンテンツの URL を出力する
   - 非公開コンテンツと無効な URL を除外する

6. 404 ページを作る
   - `app/error.vue` を追加する
   - 404 とその他のエラーの表示を分ける
   - トップ、記事一覧、検索への復帰導線を整える

7. 公開用コンテンツを追加する
   - 技術記事と読了本の原稿、画像、公開日を整理する
   - Markdown と frontmatter を追加する
   - 表記、リンク、画像、公開状態を校正する
   - 一覧、検索、タグ、アーカイブ、関連記事を実データで確認する

8. 既存 Cloudflare 環境への移行を準備する
   - Pages / Workers、接続リポジトリ、本番ブランチ、ビルド設定を確認する
   - `build` と `generate` を実行し、生成成果物をローカルで確認する
   - 旧 URL を収集し、新 URL との対応表を作る
   - 必要な 301 リダイレクトとプレビュー環境の `noindex` を設定する
   - Cloudflare のプレビュー環境で本番相当の確認を行う

9. Cloudflare の本番ブログを置き換える
   - Cloudflare の接続先を本リポジトリと本番ブランチへ切り替える
   - 既存ドメインを新しいデプロイへ割り当てる
   - canonical、OGP、RSS、サイトマップ、404、リダイレクトを確認する
   - 問題がある場合に旧デプロイへ戻せることを確認する

10. 切り替え後の検証を行う
   - HTML、XML、レスポンスコード、主要画面を確認する
   - 主要な旧 URL と 301 リダイレクトを確認する
   - Cloudflare のデプロイログと独自ドメインの状態を確認する

## テスト方針

- `vp exec pnpm build` が成功することを確認する
- `vp exec pnpm generate` が成功することを確認する
- Vite Plus が利用できない場合は `pnpm build` と `pnpm generate` を使う
- 生成成果物を `pnpm preview` で表示できることを確認する
- 各ページの title、description、canonical が正しいことを確認する
- OGP と X Card の画像 URL が絶対 URL で、実際に取得できることを確認する
- 記事の公開日、更新日、タグがメタ情報へ正しく反映されることを確認する
- `/rss.xml` が有効な XML で、公開済み記事だけを日付の降順で含むことを確認する
- サイトマップが有効な XML で、公開対象の URL だけを含むことを確認する
- RSS、サイトマップ、canonical に localhost やプレビュー URL が含まれないことを確認する
- `robots.txt` が本番とプレビューの方針に合っていることを確認する
- 存在しない URL が 404 ステータスと専用ページを返すことを確認する
- 404 ページからトップと記事一覧へ移動できることを確認する
- 新しい記事と読了本が一覧、詳細、検索、タグ、アーカイブへ反映されることを確認する
- `published: false` のコンテンツが画面、RSS、サイトマップに含まれないことを確認する
- PC / タブレット / モバイルとライト / ダークモードで主要ページを確認する
- 本番 URL で favicon、OGP 画像、RSS、サイトマップ、404 を再確認する
- 主要な旧 URL が対応する新 URL へ 301 リダイレクトされることを確認する
- リダイレクト先が存在し、チェーンやループが発生しないことを確認する
- Cloudflare のプレビュー URL が検索対象にならないことを確認する

## 完了条件

- サイト全体と各ページに適切な SEO メタ情報がある
- OGP 画像の優先順位と共通フォールバックが実装されている
- RSS とサイトマップが公開済みコンテンツから生成される
- 専用の 404 ページが正しいステータスで表示される
- 公開用の記事と読了本が追加され、仮テキストが残っていない
- `build` と `generate` が成功する
- 既存の Cloudflare 本番ドメインで新ブログを表示できる
- 旧 URL の維持または 301 リダイレクトが完了している
- 問題発生時の復旧方法が確認できている

## 前提

- 技術記事と読了本は Nuxt Content の既存 collection を使う
- `published: false` のコンテンツは画面、検索、RSS、サイトマップから除外する
- 初回公開では動的 OGP 画像生成を導入しない
- RSS は技術記事を対象とし、読了本は含めない
- コメント、アクセス解析、広告、メール購読機能は Phase 6 の対象外にする
- 既存ブログの本番ドメインと Cloudflare プロジェクトを引き継ぐ
- Cloudflare Pages / Workers のどちらかは実装開始時に既存設定から確認する
- Git リポジトリの接続変更や本番切り替えは、ローカルとプレビュー環境での検証完了後に行う
- 新しい依存関係は、必要性を説明して合意を得てから追加する
